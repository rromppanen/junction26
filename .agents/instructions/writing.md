# Writing that changes decisions

Write for one reader and one purpose. Keep the facts where their authoritative definition belongs.
Use the repository's vocabulary and required formats.

## Content and wording

- State the subject and action directly. Use concrete terms, evidence and conditions.
- Use active verbs and sentences that carry one main idea.
- Remove filler, repeated conclusions and claims without evidence.
- Keep conditions and exceptions that affect the reader's decision.
- Link to code, schemas or configuration instead of duplicating their facts.
- Separate operating instructions from history, design rationale and incident records.
- Use descriptive links and mark commands, paths and identifiers as code.
- Use lists or tables when they clarify the content. Mark quotations and cite borrowed claims.

During interactive work, give brief updates at meaningful changes in findings or direction.
Make the final response understandable without those updates or access to tool output.

## Choose the artifact

| Need | Artifact |
| --- | --- |
| Discover the project and begin work | Readme |
| Apply persistent repository boundaries | Repository instructions |
| Complete a conditional procedure | Skill |
| Recover a task across sessions | Checkpoint |
| Understand a contract or decision | Reference or decision record |

## Comments and verification

Keep comments for non-obvious constraints and caller-facing contracts. Prefer clearer names when they make commentary unnecessary.
Preserve required API documentation and legal notices.

Check named files, links and command behavior. Inspect rendered output when formatting carries meaning.
Remove a sentence when deleting it changes neither understanding nor action.
